## 1. 목적

건설 현장 안전관리자가 수행하는 법정 업무 기록을 **모듈 단위로 조합**하여 사용하는
단일 데스크톱 프로그램으로 구축한다. 모듈은 독립적으로 개발·배포·비활성화가 가능하며,
공통 기반(데이터 동기화, 문서 출력, 서류 보존, 인쇄 양식)은 프로그램 본체가 제공한다.

### 1.1 법적 배경

SMP가 지원 대상으로 삼는 안전관리자의 법정 의무는 다음과 같다.

| 업무 | 근거 법조문 |
|---|---|
| 안전관리자의 직무 | 산업안전보건법 제17조, 같은 법 시행령 제18조 |
| 관리감독자의 유해·위험 방지 업무 | 산업안전보건기준에 관한 규칙 제35조제1항, 별표 2 |
| 작업 시작 전 점검사항 | 산업안전보건기준에 관한 규칙 제35조제2항, 별표 3 |
| 근로자 안전보건교육 | 산업안전보건법 제29조, 같은 법 시행규칙 제26조·별표 4·별표 5 |
| 위험성평가 실시 | 산업안전보건법 제36조, 사업장 위험성평가에 관한 지침(고용노동부고시) |
| 산업안전보건관리비 사용 | 산업안전보건법 제72조, 건설업 산업안전보건관리비 계상 및 사용기준(고용노동부고시) |
| 서류의 보존 | 산업안전보건법 제164조 |
| 안전보건 관계 법령 의무이행 점검 | 중대재해 처벌 등에 관한 법률 제4조, 같은 법 시행령 제5조 |

> **주의**: 위 표는 SMP가 기록을 보조하는 대상 업무의 근거이며, "SMP 사용으로 법정
> 의무가 이행된다"는 의미가 아니다. 프로그램은 기록·산출 도구이고, 의무 이행 주체는
> 사업주 및 안전관리자다.

## 2. 해결하려는 문제

현재 현장 실무에서 반복 확인되는 문제:

1. **엑셀 파일 복사 관행** — 전월 파일을 복사해 덮어쓰는 방식으로 타 현장·전월 데이터가
   잔존한다. (기존 `docs/superpowers/specs/2026-09-03-legal-cost-report-design.md`에서
   실측 확인된 문제와 동일 원인)
2. **기록 산재** — TBM 일지, 순회점검일지, 교육일지, 경비 내역서가 서로 다른 파일·폴더에
   흩어져 동일 인적사항·공종·업체명을 중복 입력한다.
3. **동시 편집 충돌** — 공유폴더의 엑셀 파일을 여러 명이 열면 "읽기 전용" 또는 사본 생성으로
   갈라진다.
4. **보존 의무 대응 곤란** — 산업안전보건법 제164조에 따른 보존 대상 서류를 기간별로
   찾아내기 어렵다.

## 3. 핵심 설계 결정

### 3.0 결정 0 — 클라우드는 OneDrive

| 항목 | OneDrive | Google Drive |
|---|---|---|
| 로컬 파일 실체 | 항상 로컬 경로에 존재 | 기본이 스트리밍(가상 드라이브) — 로컬에 없을 수 있음 |
| Windows 통합 | OS 내장 | 별도 설치 |
| 파일 변경 감시 | 안정적 | 스트리밍 구조상 불안정 |
| 오프라인 작업 | 양호 | "오프라인 사용" 수동 지정 필요 |

SMP는 동기화 폴더의 파일을 직접 열어 append 하고 변경을 감시한다. 파일이 로컬에
실재해야 하므로 OneDrive를 채택한다. 현장 인터넷 단절 시에도 동작해야 한다는 요건도
같은 결론을 가리킨다.

**제약 대응**: OneDrive는 경로 길이 약 260자 제한과 파일명 특수문자 제한이 있다.
파일명은 해시·날짜 기반의 짧은 ASCII로 설계해 이를 회피한다. 폴더명에 한글을 쓰되
깊이를 3단계 이내로 제한한다.

향후 회사 조직 계정(Microsoft 365)으로 확장 시 SharePoint/Teams로 이전 가능하다.

### 3.1 결정 1 — 동기화 폴더에 공유 DB 파일을 두지 않는다

**문제**: OneDrive는 파일 단위 동기화 도구로, 파일 잠금(byte-range lock)을
지원하지 않는다. SQLite 등 단일 DB 파일을 여러 기기가 동시에 쓰면 파일 손상 또는
동기화 충돌 사본(`문서-홍길동의 충돌 사본.db`)이 발생한다.

**결정**: **기기별 단독 쓰기(single-writer-per-file) 이벤트 로그** 구조를 채택한다.

```
<클라우드 루트>/SMP/
  _공통/                       # 전원 읽기 / 관리자만 쓰기
    manifest.json              # 현장 식별자, 스키마 버전, 모듈 목록
    master/                    # 현장·업체·공종·위험요인 (개인정보 제외)
    members.json               # 사용자 등록부 (아이디, 역할, 담당 모듈)

  tbm/                         # 모듈별 폴더 — 담당자에게만 공유
    events/
      dev_a1b2c3.jsonl         # 기기 A만 append
      dev_d4e5f6.jsonl         # 기기 B만 append
    attachments/
      2026/09/<sha256>.jpg     # 사진 등 첨부 (내용주소 지정, 불변)
    roster.json                # 관리자가 배포한 해당 모듈 대상 인원

  education/                   # 타 모듈 — 담당자가 아니면 공유받지 못함
  inspection/
  legal-cost/

  _관리자/                     # 안전관리자 본인만
    master/workers.json        # 전체 인원 명부 (개인정보 원본)
    exports/
      2026-09/TBM-일지-20260916.pdf
    audit/
```

**폴더를 모듈별로 나누는 이유는 격리다.** 담당이 아닌 모듈 폴더는 클라우드 공유 자체를
하지 않으므로, 타 모듈 담당자는 앱을 우회해도 그 폴더의 존재조차 확인할 수 없다.
상세는 SMP-ARCH-002(`2026-09-16-smp-access-control.md`) 참조.

- 각 기기는 **자기 파일에만 append** 한다 → 쓰기 충돌이 구조적으로 발생하지 않는다.
- 읽기는 전체 `.jsonl`을 병합해 로컬 SQLite 캐시(프로젝션)로 재구성한다.
- 로컬 캐시는 동기화 폴더 밖(`%LOCALAPPDATA%\SMP\cache.db`)에 둔다.
- 첨부파일은 내용 해시를 이름으로 쓰므로 덮어쓰기 충돌이 없다.

**동일 레코드 동시 수정 시 병합 규칙**: 레코드 단위 LWW(Last-Write-Wins).
비교 키는 `(논리시각 lamport, 물리시각 ISO8601, deviceId)` 순. 패배한 수정은 삭제하지 않고
`superseded` 로 표시해 이력 조회에서 확인 가능하게 한다. (감사 추적 확보)

### 3.2 결정 2 — 이벤트 소싱(append-only)

레코드를 직접 덮어쓰지 않고 이벤트를 추가한다.

```jsonc
{
  "id": "evt_01J...",           // ULID (시간 정렬 가능)
  "type": "tbm.session.created",
  "module": "tbm",
  "aggregateId": "tbm_01J...",
  "siteId": "site_01J...",
  "actor": { "deviceId": "dev_a1b2c3", "userName": "홍길동" },
  "lamport": 412,
  "at": "2026-09-16T07:05:11+09:00",
  "payload": { /* 모듈별 스키마 */ },
  "schemaVersion": 1
}
```

**이유**:
- 산업안전보건법 제164조의 보존 의무 대응 시 "언제 누가 무엇을 기록했는가"가 남는다.
- 사후 수정·소급 작성 여부가 추적 가능하므로 기록의 신뢰성이 확보된다.
- 동기화 폴더 특성상 파일이 늦게 도착해도 순서를 재구성할 수 있다.

> **감사 추적에 대한 유의**: 이벤트 로그는 기록 시각을 보존하지만, 이것이 법적 증명력을
> 자동 부여하지는 않는다. 전자문서 및 전자거래 기본법상 전자문서의 효력·공인전자문서
> 요건과 SMP 로그의 관계는 **근거 확인 불가** — 별도 법률 검토가 필요하다.

### 3.3 결정 3 — 모듈 = 플러그인

모듈은 프로그램 공통 기반이 정의한 인터페이스만 구현하면 등록된다. 모듈 간 직접 참조를 금지하고,
공유가 필요한 데이터는 **공통 마스터(core)** 를 통해서만 접근한다.

```
공통 마스터 (core가 소유)
  ├─ 현장(Site)        : 현장명, 공사금액, 공기, 발주처, 원도급사   → _공통/
  ├─ 업체(Company)     : 상호, 사업자번호, 공종, 계약기간            → _공통/
  ├─ 공종(WorkType)    : 표준 공종 분류                              → _공통/
  ├─ 위험요인(Hazard)  : 공종별 표준 위험요인 사전                   → _공통/
  └─ 인원(Worker)      : 성명, 소속업체, 직종, 입·퇴소일
                         원본은 _관리자/ 에 두고, 각 모듈에는 해당
                         업무에 필요한 인원만 roster.json 으로 배포
```

TBM 모듈은 `Worker`·`WorkType`·`Hazard`를 **참조만** 하고 수정하지 않는다.
이로써 "TBM에서 입력한 인원이 교육일지에 안 잡히는" 중복 입력 문제가 해소된다.

> **개인정보 유의**: `Worker`에 성명·소속 등 개인정보가 저장된다. 수집·이용은 개인정보
> 보호법 제15조제1항제2호(법률에 특별한 규정이 있거나 법령상 의무 준수를 위해 불가피한
> 경우)에 근거하되, 주민등록번호는 개인정보 보호법 제24조의2에 따라 **저장하지 않는다**
> (법령에 구체적 근거가 있는 경우로 한정되므로, SMP는 생년월일까지만 보관).

## 4. 시스템 구성

### 4.1 패키지 구조 (모노레포)

```
apps/
  smp-desktop/            # Electron 셸 (main / preload / renderer)
packages/
  smp-core/               # 도메인 타입, 공통 마스터, 이벤트 정의, 프로젝션 엔진
  smp-sync/               # 동기화 폴더 어댑터, jsonl I/O, 병합, 무결성 검사
  smp-module-sdk/         # 모듈 등록 인터페이스 및 런타임 계약
  smp-ui/                 # Pretendard 기반 공통 UI 컴포넌트
  smp-docs/               # 문서 출력 엔진 (PDF / XLSX)
modules/
  tbm/                    # 1차 구현 모듈
  legal-cost/             # 후속: 기존 Python 코드를 TS로 재작성
  inspection/             # 후속: 순회점검일지
  education/              # 후속: 안전보건교육
  risk-assessment/        # 후속: 위험성평가
```

### 4.2 프로세스 배치

| 계층 | 위치 | 책임 |
|---|---|---|
| Renderer | Chromium | React UI, 사용자 입력, 미리보기 |
| Preload | contextBridge | 타입 지정된 IPC 창구만 노출 (`nodeIntegration: false`, `contextIsolation: true`) |
| Main | Node.js | 파일시스템, 동기화 폴더 감시, SQLite 캐시, PDF 생성 |

파일시스템 접근은 전부 Main에 둔다. Renderer에 Node 권한을 주지 않는다.

### 4.3 동기화 동작

```
[앱 시작]
  → 동기화 폴더 존재·쓰기권한 확인
  → manifest.json 읽기 (없으면 현장 초기화 마법사)
  → 자기 deviceId 등록 (최초 1회)
  → events/*.jsonl 전체 읽기 → 로컬 캐시 재구성
  → 폴더 감시(watch) 시작

[사용자 입력]
  → 이벤트 생성 → 자기 jsonl에 append (fsync)
  → 로컬 캐시 즉시 반영 (낙관적)

[타 기기 파일 변경 감지]
  → 변경분만 증분 읽기 (파일 오프셋 기록)
  → 프로젝션 갱신 → UI 자동 갱신
```

**오프라인**: 동기화 폴더가 일시적으로 접근 불가여도 로컬 캐시로 조회·입력이 가능해야
한다. 이벤트는 로컬 대기열에 쌓고 폴더 복구 시 append 한다.

**무결성 검사**: 앱 시작 시 각 jsonl의 마지막 줄이 완전한 JSON인지 검사한다. 동기화 중
잘린 줄은 격리(`events/.quarantine/`)하고 사용자에게 알린다. 조용히 버리지 않는다.

### 4.4 데이터 저장 구조

서버형 DB는 사용하지 않는다. 두 계층으로 나눈다.

```
[진실의 원천]  OneDrive/SMP/<모듈>/events/dev_xxx.jsonl   append 전용, 수정하지 않음
                      ↓ 읽어서 재구성
[조회용 캐시]  %LOCALAPPDATA%\SMP\cache.db (SQLite)      언제든 삭제 후 재생성 가능
```

캐시가 손상되어도 데이터는 소실되지 않는다. 삭제 후 이벤트를 다시 읽으면 복구된다.

```sql
-- 이벤트 원본 (전 모듈 공통)
CREATE TABLE events (
  id            TEXT PRIMARY KEY,   -- ULID (시간순 정렬 가능)
  module        TEXT NOT NULL,      -- 'daily', 'education', ...
  type          TEXT NOT NULL,      -- 'tbm.session.confirmed'
  aggregate_id  TEXT NOT NULL,      -- 대상 기록 ID
  site_id       TEXT NOT NULL,
  actor_user    TEXT NOT NULL,      -- 누가
  actor_device  TEXT NOT NULL,      -- 어느 기기에서
  lamport       INTEGER NOT NULL,   -- 순서 판정용 논리시각
  at            TEXT NOT NULL,      -- 물리 시각 (ISO8601)
  payload       TEXT NOT NULL,      -- JSON 본문
  schema_version INTEGER NOT NULL,
  source_file   TEXT NOT NULL,      -- 출처 jsonl
  source_offset INTEGER NOT NULL    -- 출처 바이트 위치
);
CREATE INDEX idx_events_agg    ON events(aggregate_id, lamport);
CREATE INDEX idx_events_module ON events(module, type, at);

-- 증분 읽기 위치 (재시작 시 처음부터 읽지 않음)
CREATE TABLE sync_cursor (
  source_file  TEXT PRIMARY KEY,
  byte_offset  INTEGER NOT NULL,
  last_read_at TEXT NOT NULL
);

-- 모듈별 조회 테이블 (이벤트에서 파생 — 언제든 재생성)
CREATE TABLE tbm_sessions    (...);
CREATE TABLE tbm_attendees   (...);
CREATE TABLE edu_courses     (...);
CREATE TABLE edu_completions (...);
```

**개인정보 취급**: 프로젝션 테이블과 이벤트 payload는 사람을 **인원 ID로만** 참조한다.
성명은 암호화된 명부 파일에서만 조회하며, 화면 표시 시점에 결합한다 (7.1절).

## 5. 모듈 인터페이스

```ts
export interface SmpModule {
  /** 고유 식별자. 이벤트 type 접두사이자 데이터 폴더명 (예: "tbm") */
  id: string;
  /** 화면 표시명 */
  name: string;
  version: string;

  /** 이 모듈이 발행하는 이벤트 스키마 (Zod) */
  events: Record<string, EventSchema>;

  /** 이벤트 → 읽기 모델 변환 정의 */
  projections: ProjectionDef[];

  /** 좌측 내비게이션에 등록될 화면 */
  routes: ModuleRoute[];

  /** 이 모듈이 생성하는 출력물 정의 */
  documents?: DocumentDef[];

  /** 참조하는 공통 마스터 (읽기 전용 선언) */
  masterRefs?: Array<'site' | 'company' | 'worker' | 'workType' | 'hazard'>;

  /** 법정 보존 기간 선언 (산업안전보건법 제164조 대응) */
  retention?: { documentKind: string; years: number; basis: string }[];

  /** 이 모듈이 요구하는 인원 명부 범위. 관리자가 roster.json 배포 시 사용 */
  rosterScope?: 'all' | 'byCompany' | 'byWorkType';
}
```

`retention.basis`에는 근거 조문을 문자열로 반드시 기재한다. 근거가 없으면
`"근거 확인 불가"` 를 기재하고, 해당 문서는 보존기간 자동 안내 대상에서 제외한다.

## 7. 보안·권한

상세 설계는 **SMP-ARCH-002 권한 및 데이터 격리 설계서**
(`2026-09-16-smp-access-control.md`)에 분리했다. 요지는 다음과 같다.

| 항목 | 방침 |
|---|---|
| Electron 강화 | `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, 원격 콘텐츠 로드 금지 |
| 신뢰 경계 | **앱이 아니라 클라우드 폴더 공유 권한**이 실제 차단선이다. 앱 내 화면 제어는 오조작 방지용 |
| 격리 단위 | 업무(모듈)별 폴더 분리. 담당이 아닌 모듈은 공유하지 않는다 |
| 역할 | 관리자 / 작성자 / 열람자 3단계. 전체 현황 조회는 관리자(안전관리자 본인)에게만 표시 |
| 사용자 식별 | 아이디는 식별 수단이며 **인증이 아니다**. 자기신고이므로 위변조 방지 수준은 낮다 |
| 권한 점검 | 앱 시작 시 선언된 역할과 실제 파일 접근 권한을 대조해 불일치를 경고 |
| 개인정보 | 전체 인원 명부는 `_관리자/`에만 둔다. 모듈 폴더에는 해당 업무에 필요한 인원만 배포 (개인정보 보호법 제3조제1항·제6항, 제29조). 주민등록번호 미수집 (같은 법 제24조의2) |
| 암호화 | 개인정보 파일만 AES-256-GCM (7.1절). 그 외는 OneDrive의 전송·저장 암호화 및 BitLocker에 의존 |

> **경고 표기 의무**: 폴더 공유 설정은 사람이 클라우드에서 직접 해야 하며, SMP는 이를
> 대신 변경할 수 없고 잘못된 설정을 탐지해 알릴 수만 있다. 공유받은 폴더에 대해서는
> SMP를 거치지 않고 원본 `.jsonl`을 직접 읽을 수 있다. 이 두 가지 구조적 한계를
> 초기 설정 화면에 명시한다.

### 7.1 암호화 범위

개인정보가 담긴 파일만 암호화한다. 전체 암호화는 PC 고장·키 분실 시 전체 복구 불가
위험이 커서 채택하지 않았다.

| 위치 | 처리 |
|---|---|
| 클라우드의 인원 명부(`workers.json`, `roster.json`) | **AES-256-GCM 암호화** |
| 클라우드의 서명 이미지 | **AES-256-GCM 암호화** |
| 클라우드의 기록 본문(`.jsonl`) | 평문. 단, 사람은 **인원 ID로만 참조**하고 성명을 직접 기록하지 않는다 |
| 내 PC의 SQLite 캐시 | 평문. BitLocker 전체 디스크 암호화로 보호 |

**핵심**: 기록 본문에 성명을 쓰지 않으므로, `.jsonl`이 유출되어도 누구의 기록인지
알 수 없다. 성명은 암호화된 명부 안에만 존재한다.

**키 관리**: 암호화 키는 Windows DPAPI로 해당 PC의 해당 사용자 계정에 묶어 보관한다
(`%LOCALAPPDATA%\SMP\key.bin`). 다른 PC나 다른 계정에서는 복호화되지 않는다.
PC 교체에 대비해 **키 내보내기·복구 기능**을 제공하며, 내보낸 키 파일은 사용자가
지정한 암호로 다시 보호한다.

근거: 개인정보 보호법 제29조, 같은 법 시행령 제30조제1항제3호,
「개인정보의 안전성 확보조치 기준」 제7조(개인정보의 암호화).

> 클라우드 계정의 2단계 인증 사용을 권고한다. 이는 SMP가 강제할 수 없는 영역이며,
> 법령상 의무 여부는 **근거 확인 불가**다.

## 8. 모듈 구성 및 단계별 계획

### 8.1 모듈 카테고리

안전관리자의 법정·실무 업무를 9개 카테고리로 묶는다. 각각 독립 모듈이며, 사용하지
않는 모듈은 설치하지 않거나 비활성화할 수 있다.

| # | 모듈 | 포함 업무 | 주요 근거 |
|---|---|---|---|
| 1 | **일상활동** (`daily`) | TBM, 순회점검일지, 작업허가서, **안전관리자 업무일지** | 산업안전보건기준에 관한 규칙 제35조 별표2·별표3 |
| 2 | **교육훈련** (`education`) | 정기·채용시·작업내용변경시·특별·관리감독자 교육, 이수현황, 미이수자 추적 | 산업안전보건법 제29조, 제32조, 시행규칙 제26조·별표4·별표5 |
| 3 | **위험성평가** (`risk`) | 최초·정기·수시 평가, 위험요인 표준 사전 | 산업안전보건법 제36조 |
| 4 | **법정경비** (`cost`) | 산업안전보건관리비, 안전관리비 I/II, 환경보전비 | 산업안전보건법 제72조 |
| 5 | **회의·협의체** (`council`) | 산업안전보건위원회, 노사협의체, 안전보건협의체, 합동점검 | 같은 법 제24조, 제64조, 제75조 |
| 6 | **보건관리** (`health`) | 건강진단, 작업환경측정, 물질안전보건자료 | 같은 법 제125조, 제129~130조, 제110조 이하 |
| 7 | **인허가·신고** (`compliance`) | 유해위험방지계획서, 선임신고, 안전검사 | 같은 법 제42조, 제17조, 제93조 |
| 8 | **사고관리** (`incident`) | 아차사고, 사고조사, 산업재해조사표 | 같은 법 제57조, 시행규칙 제73조 |
| 9 | **서류보존** | 통합 검색, 보존기간 관리, 일괄 출력 | 같은 법 제164조 |

**9번 서류보존은 모듈이 아니라 공통 기능으로 구현한다.** 모든 모듈의 기록을 가로질러
검색·보존해야 하므로, 모듈 폴더에 종속되면 목적을 달성할 수 없다.

> **안전관리자 업무일지의 법적 근거**: 산업안전보건법 시행령 제18조제1항 각 호가
> 안전관리자의 직무를 규정하나, **업무일지의 작성·비치를 직접 의무화한 조문은
> 확인되지 않았다 — 근거 확인 불가.** 실무상 직무 수행 증빙으로 사용되므로, 모듈은
> 이를 "직무 수행 기록"으로 표시하고 법정 의무로는 표시하지 않는다.

### 8.2 구현 순서

| 단계 | 내용 | 산출물 |
|---|---|---|
| 1 | 공통 기반 뼈대 — Electron 셸, 동기화 계층, 공통 마스터, 모듈 SDK, 역할·권한 점검, 암호화 계층, 관리자 초기 설정 마법사 | 빈 앱 실행 + 현장 초기화 + 공유 설정 안내표 |

| 4 | 일상활동 모듈 확장 — 순회점검일지, 안전관리자 업무일지 | 별표3 점검 항목 연동 |
| 5 | 위험성평가 모듈 | TBM·점검과 위험요인 연계 |

| 이후 | 회의·협의체, 보건관리, 인허가·신고, 사고관리 | 협의 후 착수 |
